# Дорожная карта DH-стандартизации и UX (2026–2027)

Дата: 2026-06-12. Дополняет [CLEANUP_AND_UI_ROADMAP.md](CLEANUP_AND_UI_ROADMAP.md) (инженерная гигиена, VIZ, редизайн) — здесь только научный слой (digital humanities) и продуктовый слой «спутник печатной книги + видеогалерея».

Решения владельца проекта (зафиксированы 2026-06-12):

1. Сканы и права на книгу есть; страницы PDF именуются, но **не отображаются** на сайте. Привязка к страницам — через копируемые библиографические ссылки, без факсимиле.
2. Аудитории «учёные» и «читатели» развиваются **параллельно**.
3. Слой данных: авторитетные идентификаторы (Wikidata/VIAF) + генерируемый TEI standOff + Zenodo DOI + CITATION.cff.
4. Симуляторы (звуковые законы, акцентология, орфографический гидратор): **каждое утверждение получает источник** (страница книги или именованная литература); непроверяемое помечается или убирается.

## Диагноз: что не соответствует DH-стандартам

| # | Проблема | Стандарт, который нарушен |
|---|---|---|
| 1 | Нет CITATION.cff, DOI, версионированных выпусков данных; сущности живут за hash-маршрутами `#v4/…` — нецитируемы и неархивируемы | FAIR (F1, A1), «cool URIs» |
| 2 | `canonical_id` — внутренние UUID; персоны без VIAF/Wikidata, топонимы без Wikidata/GeoNames (языки с Glottolog/WALS — уже хорошо) | Linked Open Data, 5-star data |
| 3 | Номера страниц — мёртвые данные: нет копируемой ссылки «Зализняк 2023: 157» из карточки | назначение книжного указателя |
| 4 | Происхождение производных слоёв не документировано: веса `edges`/`language_edges`/`semantic_links` — метод вычисления неизвестен читателю | прозрачность метода (DH method transparency) |
| 5 | Симуляторы выдают лингвистические утверждения без поссылочной атрибуции; не различимы текст Зализняка / редакторский слой / сгенерированный слой | провенанс, разграничение источника и редакции |
| 6 | Apache 2.0 покрывает код, но не данные; контексты и цитаты из книги — чужое авторское право, отдельного rights statement нет | лицензионная ясность FAIR (R1.1) |
| 7 | Нет стандартного экспорта (TEI, CSV, RDF) — данные нельзя переиспользовать вне приложения | FAIR (I, R) |
| 8 | Видеогалерея (191 ролик): 0 таймкодов, связи видео→сущность односторонние, связки страница↔видео нет вовсе | целостность ресурса «книга + лекции» |

## Трек A — научная инфраструктура (для учёных)

### A1. Цитируемость — быстрые победы (1 PR + 1 релиз)

1. `CITATION.cff` в корне (автор, заголовок, версия, ORCID, ссылка на демо).
2. Раздел «Как цитировать» в README и в подвале приложения.
3. Депозит версии данных (`app_data.json` + `data/modules/`) на Zenodo → DOI; бейдж в README. Далее — DOI на каждый минорный выпуск данных (concept DOI + version DOI).
4. Разделение лицензий: код — Apache 2.0; данные указателя — CC BY 4.0; цитаты/контексты из книги — отдельный rights statement («© наследники А. А. Зализняка / издательство, цитируется с разрешения, объём — справочный»). Файл `LICENSE-DATA.md`.

### A2. Стабильные URI сущностей — ✅ сделано (2026-06-13)

**Решение пересмотрено по факту данных.** Модель — глобальная идентичность по
(тип, head): каждый head уникален в своём типе, вхождения из разных книг
сливаются в одну запись (7 имён охватывают mumintroll+zametki). Поэтому
книжная область видимости URI (исходный план) **раздробила бы** слитые
сущности. Решение владельца: **глобальные URI + опциональный `?book=`**.

1. ✅ `<link rel="canonical">`, `og:url` и JSON-LD `@id` = **чистый**
   пререндеренный путь (`/<тип>/list/item/<тип>/<слаг>/`), а не hash-маршрут.
2. ✅ Кнопка «скопировать ссылку» на карточке уже есть (в приложении).
   *Осталось*: копировать именно канонический чистый URL (сейчас — hash).
3. ✅ **Заморозка слагов**: `data/slug_registry.json` (ключ — `canonical_id`),
   слаг не меняется даже при переименовании head; `scripts/build_slug_registry.mjs`
   (`npm run slug:freeze`). Редирект-таблица `data/slug_redirects.json` (пока
   пустая) + обработка в `404.html`. Введено без изменения текущих слагов.
4. *Осталось*: опциональный `?book=<id>` — фильтр карточки на одну книгу
   (изменение в приложении); канонический URL в копируемой ссылке.

### A3. Авторитетные идентификаторы — ✅ первая волна (2026-06-13)

1. ✅ Схема расширена: поле `authority: {wikidata, viaf, gnd, geonames, src}` в `entityItem`.
2. ✅ `scripts/align_authorities.py`: поиск по Wikidata (русская метка + проверка типа), вытягивает VIAF/GND/GeoNames из найденного элемента. **131 из 340** высокоуверенных совпадений записаны автоматически (`src: wikidata-auto`); остальные 209 — в `data/authority_candidates.json` с кандидатами и уровнем уверенности на **ручную проверку** (это и есть следующий шаг A3).
3. ✅ JSON-LD `sameAs` на пререндеренных страницах; на карточке — блок «Авторитетные записи» (чипы Wikidata/VIAF/GND/GeoNames).
4. **Точность важнее охвата** (научный ресурс): персоны проверяются по instance-of=человек + фамилия + инициалы + доменный фильтр (учёный/писатель/исторический; отсев актёров/спортсменов и т. п.) — пойман ложный матч «А. А. Алексеев» → кинорежиссёр. Поэтому авто-охват ~38 %, а не 80 %; остальное — через review-файл.

Осталось по A3: ручная верификация 209 кандидатов из `data/authority_candidates.json` (поле `src: manual` после подтверждения); затем — расширение на subject_index/lexicon при необходимости.

### A4. Провенанс производных данных — ✅ сделано (2026-06-13)

1. ✅ [docs/METHODS_RU.md](METHODS_RU.md) + машиночитаемый [data/provenance.json](../data/provenance.json). **Находка**: генерирующий скрипт не закоммичен — точные формулы `edges`/`language_edges`/`cross_links`/`semantic_links` **не воспроизводимы из репозитория**, честно помечены как эвристические. Метод восстановлен в общих чертах из intro-текстов приложения и анализа данных (со-упоминание с позиционным взвешиванием; semantic_links — нормированная схожесть по общим признакам).
2. Провенанс на **уровне слоя** (provenance.json), а не per-record `source_type` на 3300 записях — это соразмерно: записи указателя = `book`, правки через `editorial_flags`, а помеченные подмножества уже есть (`authority.src`, `related_entities[].src`).
3. ✅ Подпись `.chart-provenance` на графах имён и языков: «связи вычислены автоматически… поисковый сигнал, не нормативное утверждение» со ссылкой на METHODS_RU.md.

### A5. Аудит симуляторов — ✅ первая волна (2026-06-13)

## Трек B — «спутник книги и видеогалереи» (для читателей)

### B1. Навигация по «корешку книги»

Главный недостающий UX-примитив печатного спутника: ось страниц/глав.

1. Маршрут «страница N»: всё, что встречается на данной странице (имена, топонимы, лексика, термины, цитаты) — данные уже есть (`page_list`, `chapters`, `non_content_pages`).
2. Лента глав (11 глав-лекций) с плотностной мини-картой упоминаний (heatmap уже существует — переиспользовать как навигацию, а не только как витрину).
3. Точка входа на главной: «Я читаю страницу …» → поле ввода номера страницы.

### B2. Копируемые ссылки на страницы (без факсимиле)

1. На карточке у каждого номера страницы — кнопка «скопировать ссылку»: `Зализняк А. А. <Название>. С. 157` + канонический URL сущности (см. A2).
2. Эталон описания издания — в `corpus.books` (полные библиографические записи на каждый book_id: zametki, mumintroll, slovo).
3. Опционально: внутреннее (непубличное) соответствие «страница → имя файла PDF» как служебные данные для владельца.

### B3. Глубокая интеграция видеогалереи (191 ролик)

Текущее состояние: 0/191 таймкодов; видео→сущности есть (183 ролика, ~4,3 связи), обратных ссылок и связи со страницами нет.

1. **Обратные ссылки** (дёшево, сразу): на карточке сущности — чипы «упоминается в видео» (инвертировать `video_catalog.related_entities` при сборке; данные уже достаточны).
2. **Таймкоды**: импорт глав YouTube (описания роликов) скриптом; где глав нет — ручная разметка постепенно, начиная с самых длинных/популярных лекций. Deep-link `?t=` на каждый таймкод.
3. **Сущности на уровне таймкода**: `timecodes: [{t, label, entities[]}]` — тогда чип на карточке ведёт не на ролик, а на минуту.
4. **Связка видео ↔ страницы книги**: для роликов-лекций, соответствующих главам, — поле `pages`/`chapter`; экран лекции показывает «эта лекция = глава N = страницы X–Y» и наоборот.
5. Экран «Материалы → видео»: фильтр по сущности, главе, дате; сортировка по длительности/дате.

### B4. Главная как «панель задач» (совместно с фазой U1 существующей карты)

Три задачи-входа вместо витрины возможностей:

1. «Я читаю страницу …» → B1.
2. «Я смотрю видео …» → поиск по каталогу видео → карточка ролика со связями.
3. «Найти слово/имя/термин» → существующий поиск.

Симуляторы и практикум — вторичный ряд, после A5 с бейджами источников.

### B5. Карточка сущности — приоритет содержимого

Над сгибом: head + страницы с кнопкой цитаты (B2) + контексты; затем видео-чипы (B3.1); затем cross-links и authority-чипы (A3). Diary/экспорт/прочее — в меню действий.

**Первый шаг сделан (2026-06-13): связка существующих сущностей с лекциями.** `scripts/extract_entities_from_transcripts.py` — это газеттир-линкинг (НЕ открытый NER): уже известные сущности указателя (имена, топонимы, этнонимы, языки, термины; лексика исключена — слишком шумно) сопоставляются с сегментами корпуса, и пара (сущность, видео) с таймкодом первого упоминания добавляется в `video_catalog[].related_entities` с пометкой `src:"transcript"`. 807 связей; число сущностей с блоком «Видео» выросло с ~48 до ~239. Это наполняет данными B3.1/B3.2 по всему указателю. Сопоставление по-русски: стеммированные префиксы, строгие многословные фразы, якорь по фамилии с защитой от эпитетов/отчеств/коллизий. `src`-флаг сохраняет отличие авто-связей от курируемых.

Следующие шаги C3 (том II, с новыми расшифровками):

1. Извлечение **новых** сущностей (которых ещё нет в указателе) из вычитанных транскриптов — кандидаты со ссылкой на минуту; ручная верификация редактором; добавление через `import_source.py`.
2. Идентификаторы сущностей сразу канонические и мультикнижные (решение 6): том II = новый `book_id`, сущности сливаются с существующими head'ами тома I.
3. На этапе вёрстки к каждому вхождению добавляется номер страницы — указатель готов к печати **внутри** тома II и одновременно публикуется в приложении.
4. Экспорт печатного указателя (алфавитный, по типам) из тех же данных — отдельный скрипт, формат по требованиям вёрстки.

### C4. Issue-формы для исправлений

2. Метки по существующей таксономии (`type:*`, `area:*`); `issue_quality_guard.py` уже умеет проверять оформление.
