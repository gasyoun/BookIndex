# Дорожная карта DH-стандартизации и UX (2026–2027)

Дата: 2026-06-12. Дополняет [CLEANUP_AND_UI_ROADMAP.md](https://github.com/gasyoun/BookIndex/blob/main/docs/CLEANUP_AND_UI_ROADMAP.md) (инженерная гигиена, VIZ, редизайн) — здесь только научный слой (digital humanities) и продуктовый слой «спутник печатной книги + видеогалерея».

Решения владельца проекта (зафиксированы 2026-06-12):

1. Сканы и права на книгу есть; страницы PDF именуются, но **не отображаются** на сайте. Привязка к страницам — через копируемые библиографические ссылки, без факсимиле.
2. Аудитории «ученые» и «читатели» развиваются **параллельно**.
3. Слой данных: авторитетные идентификаторы (Wikidata/VIAF) + генерируемый TEI standOff + Zenodo DOI + CITATION.cff.
4. Симуляторы (звуковые законы, акцентология, орфографический гидратор): **каждое утверждение получает источник** (страница книги или именованная литература); непроверяемое помечается или убирается.

## Диагноз: что не соответствует DH-стандартам

| # | Проблема | Стандарт, который нарушен |
|---|---|---|
| 1 | Нет CITATION.cff, DOI, версионированных выпусков данных; сущности живут за hash-маршрутами `#v4/…` — нецитируемы и неархивируемы | FAIR (F1, A1), «cool URIs» |
| 2 | `canonical_id` — внутренние UUID; персоны без VIAF/Wikidata, топонимы без Wikidata/GeoNames (языки с Glottolog/WALS — уже хорошо) | Linked Open Data, 5-star data |
| 3 | Номера страниц — мертвые данные: нет копируемой ссылки «Зализняк 2023: 157» из карточки | назначение книжного указателя |
| 4 | Происхождение производных слоев не документировано: веса `edges`/`language_edges`/`semantic_links` — метод вычисления неизвестен читателю | прозрачность метода (DH method transparency) |
| 5 | Симуляторы выдают лингвистические утверждения без поссылочной атрибуции; не различимы текст Зализняка / редакторский слой / сгенерированный слой | провенанс, разграничение источника и редакции |
| 6 | Apache 2.0 покрывает код, но не данные; контексты и цитаты из книги — чужое авторское право, отдельного rights statement нет | лицензионная ясность FAIR (R1.1) |
| 7 | Нет стандартного экспорта (TEI, CSV, RDF) — данные нельзя переиспользовать вне приложения | FAIR (I, R) |
| 8 | Видеогалерея (191 ролик): 0 таймкодов, связи видео→сущность односторонние, связки страница↔видео нет вовсе | целостность ресурса «книга + лекции» |

### A2. Стабильные URI сущностей — ✅ сделано (2026-11-07)

**Решение пересмотрено по факту данных.** Модель — глобальная идентичность по
(тип, head): каждый head уникален в своем типе, вхождения из разных книг
сливаются в одну запись (7 имен охватывают mumintroll+zametki). Поэтому
книжная область видимости URI (исходный план) **раздробила бы** слитые
сущности. Решение владельца: **глобальные URI + опциональный `?book=`**.

1. ✅ `<link rel="canonical">`, `og:url` и JSON-LD `@id` = **чистый**
   пререндеренный путь (`/<тип>/list/item/<тип>/<слаг>/`), а не hash-маршрут.
2. ✅ Кнопка «скопировать ссылку» на карточке копирует именно канонический
   чистый URL (`buildCanonicalEntityUrl`, `v3_app.js`), не hash-маршрут.
3. ✅ **Заморозка слагов**: `data/slug_registry.json` (ключ — `canonical_id`),
   слаг не меняется даже при переименовании head; `scripts/build_slug_registry.mjs`
   (`npm run slug:freeze`). Редирект-таблица `data/slug_redirects.json` (пока
   пустая) + обработка в `404.html`. Введено без изменения текущих слагов.
4. ✅ **Сделано (2026-11-07)**: опциональный `?book=<id>` в копируемой
   ссылке карточки — `buildCanonicalEntityUrl(type, head, bookId)` добавляет
   scope-параметр из `it.book_id`, но только когда `corpus.books.length > 1`
   (в продакшн-данных корпус уже объединяет `mumintroll`/`zametki`/`slovo`,
   так что параметр реально появляется на ссылках). Чтение параметра уже
   умела `applyActiveBookFromQuery` (принимает и `?book=`, и `?books=`) —
   не хватало только записи со стороны карточки. Регресс-тест:
   `tests/e2e/session-features.spec.js` («copy link carries the entity's own
   book scope…»).

### A3. Авторитетные идентификаторы — ✅ первая волна (2026-06-13)

1. ✅ Схема расширена: поле `authority: {wikidata, viaf, gnd, geonames, src}` в `entityItem`.
2. ✅ `scripts/align_authorities.py`: поиск по Wikidata (русская метка + проверка типа), вытягивает VIAF/GND/GeoNames из найденного элемента. **131 из 340** высокоуверенных совпадений записаны автоматически (`src: wikidata-auto`); остальные 209 — в `data/authority_candidates.json` с кандидатами и уровнем уверенности на **ручную проверку** (это и есть следующий шаг A3).
3. ✅ JSON-LD `sameAs` на пререндеренных страницах; на карточке — блок «Авторитетные записи» (чипы Wikidata/VIAF/GND/GeoNames).
4. **Точность важнее охвата** (научный ресурс): персоны проверяются по instance-of=человек + фамилия + инициалы + доменный фильтр (ученый/писатель/исторический; отсев актеров/спортсменов и т. п.) — пойман ложный матч «А. А. Алексеев» → кинорежиссер. Поэтому авто-охват ~38 %, а не 80 %; остальное — через review-файл.

5. ✅ (H1600, 2026-07-27) `scripts/retier_authority_candidates.py` разложил 209 неподтвержденных кандидатов на `data/authority_review.{json,csv}`: **decide** — 34 (кандидат с совпавшим типом, один клик accept/reject), **research** — 139 (кандидаты есть, но тип не совпал — нужен отдельный взгляд), **none** — 36 (Wikidata ничего не вернула). `scripts/build_authority_review_sheet.py` строит интерактивный `/review-sheet` (HTML, `review/` — не коммитится) по **decide**-уровню: контекст употребления из текста + до 5 кандидатов с бейджами `тип совпал`/`точное совпадение метки`. `scripts/apply_authority_decisions.py --decisions <sheet>_decisions.json [--apply]` читает голоса (`approve`/`reject`/`defer`), пишет `authority: {..., src: "manual"}` только для explicit-approve и только для decide-уровня (research/none никогда не продвигаются автоматически); без `--apply` — dry-run отчёт, файлы не трогает. QID всегда берётся из `suggested_qid` записи — свободный текст заметки не парсится в QID.

Осталось по A3: **ручное голосование по 34 decide-строкам** (человеку — см. `@DO` в Uprava/GTD_NEXT_ACTIONS.md), затем `apply_authority_decisions.py --apply` → `npm run data:split && npm run build && npm run export:tei`. Research (139) и none (36) — отдельный проход при наличии времени, не в рамках H1600.

### B3. Глубокая интеграция видеогалереи (191 ролик)

Текущее состояние: 0/191 таймкодов; видео→сущности есть (183 ролика, ~4,3 связи), обратных ссылок и связи со страницами нет.

7. **Транскрипты уже готовы.** Все 191 видео расшифрованы Whisper; тексты и стадии вычитки живут на Яндекс.Диске, конвейер отслеживается в `video-archive.xlsx` (≈237 часов видео, многостадийная вычитка волонтерами, цель — печатный «II том Популярных лекций для юношества»).
8. **Английский слой — только метаданные.** Английский README-раздел, CITATION.cff, метки в JSON-LD, `<meta>` на страницах сущностей. UI остается русским.
9. **Полные транскрипты публичны уже сейчас** (видео и так открыты на YouTube); публикация текста не ждет выхода печатного тома.
10. **Трекер конвейера переезжает в репозиторий**: статусы по видео — в данных репо + генерируемый дашборд; xlsx выводится из обращения.
11. **Том II индексируется «index-first»**: сущности извлекаются из транскриптов уже сейчас, номера страниц привязываются на этапе верстки; спутник выходит вместе с книгой.
12. **Волонтерский вклад — через issue-формы**: кнопка «сообщить об ошибке» на карточках, предзаполняющая GitHub issue form слагом сущности.

### C2. Трекер производства: данные в репо + дашборд

1. `data/video_pipeline.json`: по видео — id (совпадает с `video_catalog.id`), стадия, исполнители, даты, ссылки на Диск. Однократный импорт из `video-archive.xlsx` скриптом, далее правки только в JSON.
2. Генерируемый маршрут-дашборд (или статическая страница в `docs/`): прогресс по стадиям, давно висящие задания, сводка часов. Доступен волонтерам по ссылке.
3. `video-archive.xlsx` удаляется из git после миграции (бинарный, неревьюируемый, уже расходится с действительностью).

### C3. Том II «index-first»

**Первый шаг сделан (2026-06-13): связка существующих сущностей с лекциями.** `scripts/extract_entities_from_transcripts.py` — это газеттир-линкинг (НЕ открытый NER): уже известные сущности указателя (имена, топонимы, этнонимы, языки, термины; лексика исключена — слишком шумно) сопоставляются с сегментами корпуса, и пара (сущность, видео) с таймкодом первого упоминания добавляется в `video_catalog[].related_entities` с пометкой `src:"transcript"`. 807 связей; число сущностей с блоком «Видео» выросло с ~48 до ~239. Это наполняет данными B3.1/B3.2 по всему указателю. Сопоставление по-русски: стеммированные префиксы, строгие многословные фразы, якорь по фамилии с защитой от эпитетов/отчеств/коллизий. `src`-флаг сохраняет отличие авто-связей от курируемых.

Следующие шаги C3 (том II, с новыми расшифровками):

1. Извлечение **новых** сущностей (которых еще нет в указателе) из вычитанных транскриптов — кандидаты со ссылкой на минуту; ручная верификация редактором; добавление через `import_source.py`.
2. Идентификаторы сущностей сразу канонические и мультикнижные (решение 6): том II = новый `book_id`, сущности сливаются с существующими head'ами тома I.
3. На этапе верстки к каждому вхождению добавляется номер страницы — указатель готов к печати **внутри** тома II и одновременно публикуется в приложении.
4. Экспорт печатного указателя (алфавитный, по типам) из тех же данных — отдельный скрипт, формат по требованиям верстки.
